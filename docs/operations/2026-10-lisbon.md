# Lisbon GIRA integration — 2026-10-07

## Source

[Gira+](https://github.com/rt-evil-inc/gira-mais/tree/ac0279d5f33c03384cbbd4dfeb01ed1f5574f479/src/lib/vaimoo-api) identifies the current public VAIMOO Firestore station collection and GIRA tenant `P1/EML/EML/`. OpenBike independently implements the REST wire format; it does not include Gira+ GPL application code, credentials, rider APIs, unlock logic, or its heuristic counts of unlockable bikes.

Read-only endpoint: `https://firestore.googleapis.com/v1/projects/vaimoorotterdam/databases/(default)/documents:runQuery`. A fixed query selects `docking-stations` for that tenant only. No API key or authentication was required by the live endpoint. The collection's data license is not declared; catalog licensing stays unknown rather than assuming Gira+'s code license or a separate EMEL open-data license applies.

## Contract

- `DockingStationId`, `Name`, `Location.geoPointValue`, and `DockLimit` supply station metadata. Virtual stations are omitted; another tenant aborts the snapshot.
- `AvailableBikes` and `FreeDocks` remain explicit provider counts. Return spaces are never computed by subtracting bikes from capacity. Missing, negative, noninteger, or capacity-exceeding free-space counts are unknown.
- Known available states: `AVAILABLE`, `IN_USE`, `LIMITED_USE`. `DISABLED`, `UNAVAILABLE_BY_SYSTEM`, `UNAVAILABLE_BY_OPERATOR`, and `UNKNOWN` are closed. Unrecognized states remain unknown. The official app/Gira+ uses `ServiceStatus` rather than `IsActive` for service availability.
- The station collection gives no bike-type breakdown or physical station heartbeat. `station_last_reported` stays null and availability confidence is medium. Responses include a source-timestamp warning.
- [Firestore readTime](https://firebase.google.com/docs/firestore/reference/rest/v1/projects.databases.documents/runQuery) dates the strongly consistent database snapshot. It is used as the provider observation time, never replaced by a local fetch clock. [Document updateTime](https://firebase.google.com/docs/firestore/reference/rest/v1/projects.databases.documents) means last changed, not last checked; it stays intact in the raw cached response. A provider that stops writing could therefore leave old physical readings in a current database snapshot; OpenBike cannot infer a missing telemetry heartbeat.
- One query, maximum 1,001 documents: more than 1,000 rejects truncation. Existing 4 MiB, depth, timeout, reviewed-host limits apply. POST redirects are rejected. Queries are fixed code, not caller input.
- Existing per-system Durable Object single-flight, 60-second provider TTL, shared map cache, warmup, rate limits and global map-work allowance apply. No client Firebase dependency, per-visitor subscription, new service or paid account.

## Map-cache rollout

The production MCP passed Lisbon pickup, return and station-detail checks, but the initial map snapshot returned 503. The map route rejected budget-denied work before consulting the already-populated per-system Durable Object. Its previous 128-unit reservations could also lose unused allowance when short-lived isolates exited. Refresh work now reserves exactly one unit per operation, including concurrent requests. At the limit, both map routes can read retained data without starting provider requests, preserving its original timestamps and existing age checks. The 25,000/day and 500,000/month limits were neither increased nor reset.

Regression coverage proves that cache-only reads never fetch upstream, even with force-refresh or stale-while-revalidate requested, and fail when no snapshot exists. It also covers five simultaneous one-unit reservations and budget-denied map responses from retained storage. These are correctness checks; no production latency improvement is inferred from them.

The all-city staging smoke passed 18 of 19 cities, including Lisbon. London returned `STALE_DATA` under the strict 180-second check; this is recorded separately from the Lisbon rollout rather than described as an all-city pass.
